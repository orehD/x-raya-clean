# Как из фразы рекрутера получается набор запросов

Весь путь от свободного текста до готовых запросов: разбор фразы, структурированный профиль
поиска, генерация синтаксиса под каждый канал.

Всё, что описано ниже, происходит **в браузере**, в `index.html`. Сервер в этом не участвует:
он нужен только там, где требуется чужой ключ (модель, проверка выдачи, контакты).

---

## Общая схема

```
"сеньор python разработчик Москва Django"
            │
            ▼
   ┌────────────────────┐
   │ Уровень 0          │  index.html → validateQuery()
   │ валидация текста   │  отсекает мусор без обращения к сети
   └────────┬───────────┘
            ▼
   ┌────────────────────┐
   │ Уровень 1          │  index.html → parse()
   │ разбор словарями   │  роль · технологии · город · грейд
   └────────┬───────────┘
            │  не хватило?
            ▼
   ┌────────────────────┐
   │ Уровень 2          │  index.html → aiInterpret() → POST /api/ai
   │ разбор моделью     │  возвращает тот же профиль, но собранный LLM
   └────────┬───────────┘
            ▼
   ┌────────────────────┐
   │ Профиль поиска     │  {role, techs, city, grade}
   │ (правится руками)  │  рекрутер может поменять любое поле
   └────────┬───────────┘
            ▼
   ┌────────────────────┐
   │ Генерация          │  index.html → build()
   │ каналов ≈30        │  на каждый канал свой синтаксис
   └────────┬───────────┘
            ▼
    карточки: строка запроса + готовая ссылка
```

Ключевая идея: **разбор отделён от генерации**. Разбор превращает свободный текст в набор
сущностей, генерация превращает сущности в синтаксис конкретной площадки. Это две независимые
задачи, и результат каждой из них самостоятелен.

---

## Уровень 0. Валидация без сети

`validateQuery(raw)` — детерминированная проверка до всего остального.

Режет только явный брак: пустую строку без букв, слишком длинный текст (200 символов для
обычного запроса, 9000 для вставленной вакансии, 2000 для описания подборки). Ничего не
угадывает и в сеть не ходит.

Смысл уровня: не тратить ни модель, ни время рекрутера на заведомо непригодный ввод.

---

## Уровень 1. Разбор словарями

`parse(raw)` — основной путь. Работает мгновенно, без сети, и покрывает большинство запросов.

Внутри четыре справочника, зашитых прямо в страницу:

| Справочник | Объём | Что содержит |
|---|---|---|
| `CITIES` | 21 город | русское и английские написания, id для hh.ru и Habr, разговорные формы («мск», «питер», «нерезиновая») |
| `TECH` | 69 технологий | каноническое имя, признак языка программирования, ключ для GitHub, алиасы (`go`→`golang`, `c#`→`net`) |
| `GRADES` | 5 грейдов | intern / junior / middle / senior / lead, ключевые слова и алиасы |
| роли | 130 записей | каноническое имя, 8–14 синонимов на двух языках, категория IT/не-IT, флаги, типовой стек |

Разбор идёт по алиасам: строка нормализуется, из неё вынимаются совпадения по каждому
справочнику. Роль ищется по синонимам, а не по точному названию — «питонист», «python
developer» и «разработчик python» ведут к одной записи.

Если роль не опознана, но в тексте есть язык программирования, подставляется обобщённая
IT-роль. Если технологий нет вообще — обобщённая не-IT.

Уровень детерминирован: один и тот же текст всегда даёт один и тот же профиль, без обращения
к модели и без вариативности.

---

## Уровень 2. Разбор моделью

Включается в двух случаях: рекрутер сам поставил галочку «AI-анализ запроса», либо словарь
промахнулся и сработал автоматический фолбэк.

Запрос уходит на свой сервер (`POST /api/ai`), тот подставляет ключ и зовёт
OpenAI-совместимого провайдера. Ключ в браузер не попадает никогда.

Модель обязана вернуть строгий JSON:

```json
{
  "category": "it",
  "role": "Python-разработчик",
  "synonyms": ["python developer", "бэкенд-разработчик python", "питонист", "..."],
  "technologies": ["Python", "Django", "PostgreSQL"],
  "city": "Москва",
  "seniority": "senior"
}
```

Дальше `specToBase()` превращает этот JSON в **тот же самый профиль**, что делает словарь.
С этого момента генерация не знает и не должна знать, откуда взялся профиль.

Разбор кешируется в браузере на 30 дней по тексту запроса — повторный ввод той же роли
отвечает мгновенно и не тратит токены.

## Профиль поиска

Результат любого из уровней — одна структура:

```js
{
  role:  { key, ru, cat: 'it'|'nonit', syn: [...], ghKw, stack: [...], flags: [...] },
  techs: [ { c: 'Python', lang: 1, gh: 'python' }, ... ],
  city:  { ru: 'Москва', en: ['Moscow'], hh: 1, habr: 'c_678' },
  grade: { key: 'Senior', kw: 'senior', qids: '...' }
}
```

Рекрутер видит его как «Профиль поиска» и правит любое поле руками. Каждая правка
пересобирает все запросы заново. У каждой технологии есть режим **обязательно / желательно /
исключить** — он меняет то, как она попадёт в синтаксис: в `AND`, в `OR`-группу или в `NOT`.

## Генерация запросов

`build(profile)` собирает набор карточек: около тридцати, точное число зависит от роли и стека.
Каждая карточка — строка запроса плюс готовая ссылка. Синтаксис у каждого канала свой, и одна
и та же мысль рекрутера выражается в них по-разному.

### Google X-Ray

Поиск по чужому сайту через Google. Единственный способ достать LinkedIn из России.

```
site:linkedin.com/in ("Python" OR "Django") ("python developer" OR "бэкенд-разработчик")
  ("Moscow" OR "Москва") "senior" -jobs -вакансия -курсы
```

Собирается из кусков: домен, группа языков через `OR`, группа синонимов роли через `OR`,
группа города, грейд, и хвост исключений (`NOISE`) — он отсекает вакансии, курсы и агрегаторы,
которые иначе забивают выдачу.

### Нативный язык площадки

Там, где у площадки есть свой язык, X-Raya использует его, а не X-Ray. Пример hh.ru:

```
POSITION:((Python OR Django) AND ("python developer" OR "питонист"))
  AND KEYWORDS:(Python OR Django OR PostgreSQL)
  NOT POSITION:("стажер" OR "trainee" OR "intern")
```

Плюс параметры в самой ссылке: `area` — id города из справочника, `exp_period=all_time`,
`job_search_status=active_search`. То есть часть фильтра живёт в синтаксисе, часть в URL.

### Параметрические ссылки

Habr Career и GitHub не имеют текстового языка запросов — у них фильтры параметрами:

```
https://career.habr.com/resumes?q=python+Django&qids[]=<грейд>&locations[]=c_678
https://github.com/search?q=type:user location:"Moscow" language:python "python developer"
```

Поэтому в справочниках и хранятся id: `hh: 1`, `habr: 'c_678'`, `gh: 'python'`. Без них
параметрическую ссылку не собрать.

### Группы каналов

Семь групп, по смыслу источника:

| Группа | Что там |
|---|---|
| `pro` | LinkedIn, hh.ru, Habr Career, GitHub, TenChat |
| `community` | профильные комьюнити и портфолио |
| `role` | площадки под конкретную роль (дизайн, логистика, data) |
| `exec` | руководители и основатели |
| `conf` | конференции и митапы |
| `social` | соцсети через X-Ray |
| `comp` | соревнования по коду |

Плюс отдельная группа `candy` — запросы во внутреннюю базу, о ней ниже.

## Два языка Candy

Внутренняя ATS понимает два разных языка.

### Язык 1: поисковая строка

Простой синтаксис для обычного поиска по базе:

```
specialization:"Python Developer" AND level:Senior AND location:"Москва" AND file:"Django"
```

Собирается детерминированно, без модели. Специализация подбирается из справочника на
192 позиции сопоставлением с синонимами роли: точное совпадение важнее вхождения, вхождение
важнее общего корня. Результат — ссылка вида
`candy.tbank.ru/candidates/search/extended?query=<...>`.

Оговорка про `level:` вынесена в интерфейс: этот фильтр показывает только кандидатов с
пройденными секциями на уровень, поэтому на нём выдача часто схлопывается в ноль.

### Язык 2: JSON-фильтр подборок

Сохранённые подборки задаются не строкой, а деревом условий. Описание языка — в отдельном
документе [CANDY.md](CANDY.md).

---

## Точки расширения

Пайплайн распадается на две самостоятельные части, и результат каждой применим отдельно.

**Профиль поиска** — результат разбора. Структурированные сущности, извлечённые из свободного
текста: роль с синонимами, стек, город, грейд. Не зависит от того, как дальше будет собран
синтаксис.

**JSON-фильтр подборки** — результат генерации для внутренней базы. Описывает набор условий,
по которым ATS возвращает кандидатов. Исходный текст запроса при этом сохраняется отдельно:
фильтр всегда огрубляет формулировку, и восстановить исходный смысл по одним условиям нельзя.

Серверные интерфейсы — в [API.md](API.md).
