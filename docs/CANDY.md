# Подборки Candy: из фразы в JSON-фильтр

Подборка — это сохранённый в ATS набор условий, по которому база отдаёт список кандидатов.
Задаётся не строкой поиска, а деревом условий в JSON. Язык богатый, синтаксис неочевидный,
и половина ошибок в нём не вызывает отказа: ATS молча возвращает пустую выдачу.

X-Raya собирает такой JSON по описанию словами и проверяет его до того, как рекрутер
что-то вставит в базу.

---

## Движок candy-json (основной путь)

С сентября 2026 фильтр собирает не модель напрямую, а движок в `candy-json/`,
опирающийся на выгруженные справочники Candy в `candy-kb/`.

Разделение ответственности такое: **модель раскладывает запрос по полям и ставит
ссылки на справочники, а конкретные id, коды и операторы подставляет движок** и сразу
сверяет их со схемой поиска. Поэтому выдуманный id специализации или несуществующий
оператор невозможны архитектурно, а не потому, что промпт это запретил.

```
"бывшие сотрудники — продуктовые аналитики"
            │
            ▼
   POST /api/candy { task, pw, sessionId }
            │
            ▼
   модель → спека с ref-ссылками:
     { field: "hiringProcesses.specializationId",
       ref: { kind: "specialization", query: "Продуктовый аналитик" } }
            │
            ▼
   движок разрешает ссылки по candy-kb, проверяет операторы по filter.json,
   собирает nested_any-цепочки и блок исключений
            │
            ├── нашлось несколько специализаций → status: clarify,
            │   вопрос рекрутеру со списком вариантов (CJM: «XRaya уточняет запрос»)
            │
            ▼
   status: ok → готовый фильтр + пояснение, из каких источников взяты данные
```

Что это даёт по сравнению с прежней схемой: значения приходят из справочников,
неоднозначность превращается в вопрос вместо догадки, а вместо одного выстрела
получается диалог — рекрутер уточняет запрос репликами, как в CJM.

**Диалог.** Сессия живёт 30 минут в памяти сервера, `sessionId` возвращается в ответе
и приходит обратно со следующей репликой. Ответить можно номером варианта
(«вариант 1», «1 и 3») или словами — простые ответы разбираются без обращения к модели.

**Подпись.** Готовый фильтр получает `#name` («X-Raya · <запрос рекрутера>») и
`#description` с пояснением. В интерфейсе Candy видно, откуда взялась подборка.

**Запасной путь.** Если `candy-json` не загрузился или выключен через `CANDY_ENGINE=off`,
сервер работает по прежней схеме: промпт `candy-prompt.md` + валидатор `podCheck()`
на клиенте. Ветка `fix` (починка синтаксиса) всегда идёт по старому пути — движку
чинить за собой нечего.

**Где что лежит:** `candy-json/README.md` — устройство движка, `candy-json/EVALS.md` —
история замеров качества, `node candy-json/audit.js` — сверка справочников,
`node candy-json/schema-check.js` — валидация фильтров по схеме поиска.

## Как работает запасной путь (промпт)

```
"бывшие сотрудники — продуктовые аналитики, уволились без негатива"
            │
            ▼
   POST /api/candy  { task, pw }
            │
            ▼
   сервер добавляет системный промпт (candy-prompt.md, ~35 КБ:
   схема полей, 7 правил синтаксиса, справочники ID, 7 рабочих примеров)
   и текущую дату — у модели нет часов, а «за последний год» надо
   превратить в абсолютную date_gt
            │
            ▼
   модель возвращает markdown: блок JSON + разбор по блокам
            │
            ▼
   браузер: podClean() → podJsonSrc() → JSON.parse() → podCheck()
            │
            ├─ ошибок нет ───────────► JSON выводится с кнопкой копирования
            └─ есть ошибки ──────────► одна автоматическая попытка починки:
                                       ошибки валидатора уходят обратно в модель
```

На выходе либо проверенный JSON, либо сообщение о том, что собрать не удалось.
Невалидный JSON в интерфейс не попадает.

## Язык фильтров

Дерево условий. Узел — либо логический оператор, либо поле с оператором сравнения.

```json
{ "#name": "Бывшие сотрудники ПА",
  "$and": [
    { "hiringProcesses": { "nested_any": { "filter": { "$and": [
        { "specializationId": { "string_one_of": { "values": ["<uuid>", "<uuid>"] } } },
        { "events": { "nested_any": { "filter": {
            "plainEventState": { "int_one_of": { "values": [35, 46, 54] } } } } } } ] } } } },
    { "employeeStatus": { "string_eq": { "value": "Dismissed" } } },
    { "$not": { "tags": { "text_list_matches_any_of": { "values": ["читер"] } } } }
  ] }
```

Читается так: есть процесс отбора, в котором **одновременно** нужная специализация и событие
трудоустройства; статус — уволен; тега «читер» нет.

### Семь правил, на которых ломаются генераторы

Они выведены из отладки живого агента и вынесены в начало промпта:

1. **Обёртки `filter` на верхнем уровне нет.** Условия кладутся прямо в корень.
2. **Внутри `nested_any` обёртка `filter` обязательна.** Без неё условие не применяется.
3. **`$not` оборачивает поле целиком**, а не лежит внутри него.
4. **Список ≠ скаляр.** `closingReasonsIds` — список, ему нужен `int_list_contains_any_of`.
   Скалярный `int_one_of` на нём проходит валидацию и **молча даёт ноль кандидатов**.
5. **«В одном процессе» против «в разных» — разная вложенность.** Два условия внутри одного
   `nested_any` через `$and` означают один процесс; два отдельных `nested_any` — разные.
6. **`$not` над `nested_any`** означает «ни одного такого», а не «есть не такой».
7. **Даты только абсолютные**, строкой `"YYYY-MM-DD"`. Оператора «последние N месяцев» нет.

### Операторы

| Тип поля | Операторы |
|---|---|
| текст | `text_match` (словоформы), `text_phrase` (точная фраза), `text_phrase_any_of` |
| список текстов | `text_list_phrase`, `text_list_matches_any_of`, `text_list_matches_all_of` |
| строка-enum | `string_eq`, `string_one_of` |
| список строк | `string_list_contains_any_of`, `string_list_contains_all_of` |
| число | `int_eq`, `int_one_of`, `int_gt`, `int_lt` |
| список чисел | `int_list_contains_any_of`, `int_list_contains_all_of` |
| дата | `date_gt`, `date_lt`, `date_eq`, `date_between` |
| булево | `bool_eq` |
| вложенное | `nested_any` + обязательный `filter` |

Операторов `int_ne`, `int_not_one_of`, `like`, `wildcard`, `string_ne` **не существует** —
модели их регулярно выдумывают, поэтому они внесены в валидатор как явно запрещённые.

### Схема сущностей

```
кандидат
├── name, surname, location, citizenship, birthYear, tags, employeeStatus,
│   employeeDismissalReasonIsNegative, files, offices, levels, ...
├── hiringProcesses[]            процессы отбора
│   ├── specializationId, closingReasonsIds
│   └── events[]                 события процесса
│       └── plainEventState, createdUtc
├── resumes[]
│   ├── declaredSpecialization, about, declaredSkills, workExperienceTotalYears
│   ├── workExperience[]         company, position, description, isCurrent, startDate, endDate
│   └── higherEducation[]        university, faculty, major, startYear, endYear
└── facts[]                      данные из кадровой системы
```

Полная схема с типами и списками допустимых ID — в [`candy-prompt.md`](../candy-prompt.md).

## Где лежат правила языка

Единственный источник правды по языку подборок — файл [`candy-prompt.md`](../candy-prompt.md)
в корне репозитория. В нём:

| Часть | Содержимое |
|---|---|
| 1 | Семь правил синтаксиса с примерами верного и неверного написания |
| 2 | Схема полей: типы, допустимые операторы, различия текстовых операторов |
| 3 | Готовые блоки условий: базовая гигиена, бывшие сотрудники, опыт в банках, пройденный скрининг |
| 4 | Справочники идентификаторов: состояния событий, причины закрытия процесса |
| 5–6 | Алгоритм сборки, чек-лист проверки, формат ответа |
| 7 | Запрещённые конструкции |
| 8 | Проверенные примеры, скопированные из действующих подборок |
| 9 | Известные ограничения языка |

Файл целиком уходит в модель системным промптом. Правка файла меняет поведение генератора,
пересборка кода при этом не требуется. Содержимое читается один раз и кешируется в памяти,
поэтому изменения применяются после перезапуска процесса.

Валидатор — отдельная реализация тех же правил, независимая от модели. Он живёт в `index.html`
в таблицах `POD_OPS`, `POD_FIELDS`, `POD_FAKE_OPS` и функции `podCheck()`. При добавлении новых
полей или операторов в `candy-prompt.md` их нужно внести и туда, иначе валидатор пометит
корректную конструкцию как неизвестное поле.

## Валидатор

Живёт в браузере, `podCheck()` в `index.html`. Работает детерминированно, без модели, и
ловит именно те ошибки, на которые ATS не жалуется:

- обёртка `filter` на верхнем уровне
- `nested_any` без внутреннего `filter`
- `$not` внутри поля
- скалярный оператор на списочном поле
- несуществующие операторы
- поле, которого нет в схеме
- дата не в формате `YYYY-MM-DD` (в том числе плейсхолдер вроде `<сегодня минус 3 месяца>`)
- значение `employeeStatus` вне enum
- `values` вместо `value` и наоборот

Проверен на действующих подборках: они проходят без замечаний.

Отдельно `podClean()` снимает то, что ломает `JSON.parse` и саму ATS: комментарии `//` и
`/* */` внутри JSON (модели любят пояснять фильтр прямо в нём) и висячие запятые.
Кавычки учитываются, чтобы `http://` внутри строкового значения не пострадал.

## Исходный запрос и фильтр

Фильтр — огрубление формулировки. «Сильный аналитик с опытом в финтехе» превращается в набор
булевых условий, и слово «сильный» в них не выражается. Поэтому исходный текст запроса
сохраняется отдельно от собранного фильтра.

Серверные интерфейсы — в [API.md](API.md).
