# candy-json — движок JSON-подборок Candy (X-Raya)

Переводит бизнес-запрос рекрутера в валидный JSON-фильтр поиска кандидатов Candy.
Fail-closed по построению: id, коды и операторы модель не пишет никогда — она ставит
ref-ссылки на справочники, а подставляет значения движок из базы `../candy-kb`.

**Качество** (`node eval.js`, 29 реальных подборок): доходит до фильтра 28/29,
полнота 69%, точность по сужающим условиям 66%. Модель — `openai/gpt-5-mini`
через VseGPT, ~1 ₽ за запрос. Полная история замеров и разбор — [EVALS.md](EVALS.md).

> ⚠️ Про цифры. Ранние 90–93% были получены на восьми кейсах, формулировки которых
> я писал сам, уже зная эталонный фильтр, — это давало невольную подсказку. Текущая
> метрика строже: запросы берутся дословно из описаний боевых подборок, на уточняющие
> вопросы отвечает симулятор рекрутера, знающий только исходную формулировку.
> У такой метрики есть объективный потолок: описания неоднозначны («Потенциальные
> ML-продакты»), и два рекрутера соберут разные, но одинаково правильные фильтры.
> Поэтому полнота (не потерять названное рекрутером) важнее точности: лишнее условие
> видно в таблице проверки и снимается одной репликой в диалоге.

## Конвейер

```
запрос рекрутера
   │  llm.js (VseGPT) + prompts.js — интерпретация в DSL-спеку с ref-ссылками
   ▼
DSL-спека  { conditions: {all/any/not/same/field+op+value|ref}, exclusions }
   │  resolve.js — Field Resolution: поле→модель, оператор→filter.json, ref→справочники
   ▼         └── неоднозначно/не найдено → status:'clarify' + вопросы с вариантами
таблица проверки (все статусы «найдено»)
   │  builder.js — nested_any-цепочки, same-группы, $or-разворот наборов, блок исключений
   ▼
JSON-фильтр  →  validateFilter (повторная сверка со схемой)  →  status:'ok'
```

Диалог (`dialog.js`) закрывает уточнения: ответы «да/нет» и «первый вариант» разбираются
без обращения к модели, промах мимо схемы догружает полный список полей, ошибка сборки
возвращается модели на самопочинку.

## Файлы

- `kb.js` — доступ к базе: разрешение путей полей, ранжированный поиск по справочникам
  (стемминг, RU→EN синонимы), готовые наборы значений
- `operators.js` — канонический реестр из filter.json: 20 операторов, привязка к полям, enum
- `builder.js` — DSL → фильтр, `exclusionBlocks`, `validateFilter`
- `resolve.js` — Field Resolution + таблица проверки (формат промпта Алисы)
- `engine.js` — `buildQuery(spec)` → ok / clarify / error
- `prompts.js` — системный промпт; шпаргалка полей и каталог наборов генерируются из базы
- `llm.js` — VseGPT: ретраи на rate-limit и обрыв ответа, temperature 0
- `index.js` — `ask(query)` (полный конвейер), `buildQuery(spec)` (без LLM)
- `cli.js` — `node cli.js "запрос"` / `--spec file.json` / `--prompt`
- `test.js` — регресс: боевые фильтры, голдены, fail-closed, диалог (50 ✓)
- `eval.js` — метрика качества на эталонах (`node eval.js [N]`)
- `audit.js` — аудит базы знаний: ссылочная целостность, дубли, enum, разрешимость

## Экономия токенов (retrieval вместо полной схемы)

Полная схема — 196 полей и ~24k символов на каждый запрос. В промпт идёт горячее ядро
(27 полей, покрывающих все боевые подборки) плюс ветки, которые триггерит сам запрос;
полная схема догружается вторым кругом, только если модель промахнулась. Итог: ~15k
символов, из них большая часть — правила и каталог наборов.

## Готовые наборы значений

`candy-kb/value_groups.json` — выверенные рекрутерами наборы, которые движок подставляет
целиком вместо фантазии модели. Это главный источник точности по значениям:
- **valueGroup**: банки (14), бигтех, топ-вузы, юрвузы, английский B1/B2+, ML-ключевики, ценные бумаги
- **roleVariants**: тимлид, БА, ПА, риск-менеджер, лид-дизайнер, продакт, стратег, Java
- **stageGroup**: дошли до трудоустройства (36 кодов), до оффера, прошли скрининг/техничку/финал и др.

Наборы под одиночным оператором (`text_phrase`) движок разворачивает в `$or` — ровно так,
как устроены боевые подборки.

## Тесты и метрика

`node test.js` — 50 ✓ / 0 ✗: валидация 23 боевых фильтров и 12 примеров, 5 голденов
(движок пересобирает подборку из спеки и результат совпадает с боевым фильтром),
fail-closed на мусоре, разрешение справочников, диалоговые доуточнения.

`node eval.js` — полный конвейер на 29 кейсах: описания боевых подборок и примеров
из таблицы Алисы. Кейсы собираются автоматически, четыре подборки-донора few-shot
исключены из выборки. На уточняющие вопросы отвечает симулятор рекрутера (LLM,
видит только исходную формулировку). Сравнение по нормализованным семействам
операторов (`string_eq` ≈ `string_one_of`), служебный блок исключений не учитывается.
Результаты со собранными фильтрами сохраняются в `.eval-last.json`.

`node audit.js` — сверка справочников между собой и с боевыми подборками.

`node schema-check.js` — формальная валидация фильтров по `filter.json` (JSON Schema
поиска Candy). Отвечает на вопрос «примет ли окно поиска этот JSON» без догадок.
На последнем прогоне: все 28 наших фильтров валидны; невалидны две боевые подборки
(«Юристы HQ», «BA с английским») — в них оператор `text_phrase_any_of`, которого
в актуальной схеме нет.

## Известные дефекты боевых данных (audit.js)

1. Подборка «Бывшие сотрудники ПА»: `specializationId …91581dd68f27` отсутствует в
   справочнике, похоже на опечатку в `…91581dd6896f` (Продуктовый аналитик).
2. В старых боевых подборках встречаются 43 кода этапов, которых нет в актуальном
   справочнике. Это не пробел: справочник «Коды этапов и статусов отбора» содержит
   все коды, которые действительно нужны, а остальные помечены `legacy` и выведены
   из поиска — новые подборки собираются только из актуальных значений.
3. `text_phrase_any_of` встречается в двух старых пресетах, но отсутствует в filter.json —
   движок разворачивает такие перечисления в `$or` из `text_phrase`.

## Выбор модели (замеры на одинаковых кейсах)

| Модель | F1 условия | ₽/запрос |
|---|---|---|
| openai/gpt-5-mini | 90–93% | ~1.0 |
| anthropic/claude-sonnet-4.5 | 73% | ~9.4 |
| anthropic/claude-haiku-4.5 | 63% | ~3.3 |

Разница в качестве между моделями оказалась в пределах шума, поэтому решает цена.
Замеры Sonnet и Haiku сделаны до внедрения наборов значений и уточнённых правил.

## Осознанные ограничения

**Локации.** `locationId` — это uuid, и их слишком много, чтобы вести справочник.
Фильтр по городу строим текстом: `location`, `facts.location`, `resumes.location`.

**Коды этапов.** Используем только те, что есть в справочнике «Коды этапов и статусов
отбора». Коды из старых подборок помечены `legacy` и в новые фильтры не попадают.

**Теги.** Справочник тегов отложен до следующей итерации. Единственный используемый
тег — «читер» в блоке исключений; поиск по произвольным тегам пока не предлагаем.

## Где ещё лежит качество (по данным последнего прогона)

Самые частые потери — воронка: `plainEventState` (4), `closingReasonsIds` (3),
`events.createdUtc` (3). Значит следующий шаг — не правки промпта, а обогащение
справочников: наборы `stageGroup` под формулировки вроде «без отказа на финальном
интервью», «проходил секции», и расшифровка 42 кодов этапов, которых нет в справочнике.

Самое частое лишнее — `resumes.workExperience.position` (9) и `specializationId` (5).
Это следствие неоднозначности описаний: половина боевых подборок ищет роль только
по специализации процесса, половина — ещё и по резюме, и угадать это из текста нельзя.
Правило намеренно смещено в сторону полноты.
