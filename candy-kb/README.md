# Candy JSON-подборки — база знаний (X-Raya)

Нормализованная база для модуля составления JSON-запросов к поиску кандидатов Candy (Т-Банк).
Собрана 2026-09-03 из папки `~/Downloads/JSON` (14 файлов: транскрибация встречи, промпт текущего
ассистента, справочники в rtf/xlsx/csv). Цель — движок «бизнес-запрос рекрутера → валидный
JSON-фильтр», который дальше встраивается по API в интерфейсы (поиск Candy, хендбук подборок).

## Контекст (из транскрибации «Запросы в Candy»)

- Candy уходит от монолитных подборок к **отдельным критериям**, которые комбинируются через «И»
  и проливаются в URL — ссылка воспроизводит одну и ту же выдачу у любого рекрутера.
- До конца сентября 2026 бэк готов, фронт в работе. Пока критериев нет, работаем итерациями:
  1. **Итерация 1** — ассистент составляет JSON, рекрутер вставляет его в dev-окно поиска.
  2. **Итерация 2** — JSON + автосоздание подборки в хендбуке по API (галочка «доступ по API»;
     фронт Candy тянет из хендбука название критерия, JSON и доступы; кэш обновляется пару минут).
  3. **Итерация 3** — доп. критерии + бесшовная интеграция в контур Candy (встреча с тимлидом Колей,
     фронтендером; консультации по справочникам — Коля Долгополый).
- UX-цель: диалоговое окно, ассистент доуточняет запрос как аналитик, объясняет, по каким полям
  искал (запрос Олеси — прозрачность источников), кнопки «шире/уже» как в X-Raya.
- Данные не чувствительные (справочники без персухи) — можно использовать внешние модели.
- База для проверки качества — уже созданные подборки (`presets.json`) и запросы из канала
  «проработка базы».

## Структура JSON-запроса (по образцу пресетов и промпта)

```json
{ "$and": [
  { "hiringProcesses": { "nested_any": { "filter": { "$and": [
      { "specializationId": { "string_eq": { "value": "<uuid из specializations.json>" } } },
      { "events": { "nested_any": { "filter": {
          "plainEventState": { "int_one_of": { "values": [65, 66] } } } } } }
  ] } } } },
  { "$not": { "employeeStatus": { "string_eq": { "value": "Employed" } } } }
] }
```

- Оператор всегда обёрнут: `{"поле": {"оператор": {"value"|"values": …}}}`.
- Nested-поля — только через `<контейнер>.nested_any.filter.<относительный ключ>`;
  второй уровень — цепочка (`resumes.nested_any.filter.workExperience.nested_any.filter.position`).
- Условия одного объекта (один процесс отбора / одно резюме) группируются в одном `nested_any`.
- Стандартный блок исключений (сотрудники/читеры/негативное увольнение): четыре `$not` —
  employeeStatus=Employed, tags содержит «читер», employeeDismissalReasonIsNegative=true,
  facts.employeeDismissalReasonId ∈ [3,4].

## ⚠️ Чего не хватает (запросить у Алисы)

1. **`filter.json` (207 КБ)** — единственный источник истины по операторам и их привязке к
   operatorSet. В переданной папке его нет (виден в скриншоте базы ассистента).
   Пока опираемся на наблюдаемые операторы из пресетов.
2. **JSON Schema** запроса — промпт на неё ссылается, файла нет.
3. Библиотека этапов с описаниями «что за этап и когда отсекаем» — Даня планировал собрать сам.
4. Справочники локаций (`locationId` — uuid, напр. Москва `0c5b2444-70a0-4932-980c-b4dc0d3f02b5`
   из URL пресета) и тегов (`tagsIds`).

## Текущий ассистент (Промпт_АссистентJSON)

Работает на внутренней модели, качество «плоховато». Ключевая механика промпта, которую стоит
сохранить в новом движке: fail-closed (нет подтверждённого поля/оператора/кода — нет JSON),
Field Resolution + таблица проверки перед выдачей, запрет плейсхолдеров, только бизнес-вопросы
рекрутеру (никогда не спрашивать техполя/id), обязательный вопрос про исключения,
варианты написания для свободного текста резюме (`InferredSkills` — с заглавной I!).
